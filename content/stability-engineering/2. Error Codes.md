## 背景

很多团队一开始并不重视错误码，觉得有 HTTP Status Code、有异常栈、有日志，已经足够了。系统规模小时，这种做法通常也确实能勉强运转。

但一旦进入多系统集成、微服务拆分、跨团队协作的阶段，问题会迅速暴露：

- 同样一个报错，不同系统会用不同文案表达，导致上游根本无法稳定识别
- 有些错误是可重试的，有些需要人工介入，有些应该静默降级，如果没有标准化标识，自动化策略无从谈起
- 纯技术错误信息对研发有用，但对运营、客服、商家并不友好，缺少可沟通的抽象层
- 当系统越来越多、版本越来越多时，错误会持续增长；如果没有统一治理，最后一定会变成“谁也说不清这个错到底是什么意思”

所以错误码标准化，本质上不是为了“定义一批字符串”，而是为了建立一层跨系统、跨角色、可运营的错误语言。

## 错误码要解决什么问题

我认为一套靠谱的错误码体系，至少要同时解决四件事：

### 1. 让机器能稳定处理

机器不适合依赖自然语言做判断，因为错误文案会变、会本地化、会被不同开发写出不同风格。真正适合自动化分支的是稳定的 code。

例如：

- `AUTH_INVALID_TOKEN` 可以触发“提示重新授权”
- `UPSTREAM_RATE_LIMITED` 可以触发“指数退避重试”
- `INVENTORY_VERSION_CONFLICT` 可以触发“重新拉取最新版本后重放”

如果没有标准化 code，这些动作最终都会退化成大量脆弱的字符串匹配。

### 2. 让人能快速定位

一线研发真正关心的不是“有没有失败”，而是：

- 这是业务拒绝，还是系统故障？
- 是我自己的问题，还是下游依赖的问题？
- 根因在平台、内部服务，还是第三方平台？
- 这个问题是否可重试，是否会影响用户，是否值得夜间值班介入？

错误码如果只是一串编号，却无法帮助定位，那它的价值很有限。好的错误码应该天然服务于排障。

### 3. 让业务角色能沟通

对于商家、客服、运营来说，他们通常不关心异常名，也不关心某个 HTTP body 里的字段细节。他们需要的是更高层、可解释、可归类的结果，比如：

- 授权失效
- 库存同步失败
- 平台限流
- 商品数据某个字段不合法

这也是为什么错误码不能只停留在底层技术实现上，它最终还要承担对外沟通和知识沉淀的职责。

### 4. 让团队能持续治理

错误不是一次性定义完的。只要业务持续演进、接入平台持续增加、新功能不断上线，新的错误场景就会不断出现。

因此错误码体系除了“设计”，还必须考虑“运营”：

- 如何发现未标准化错误
- 如何避免重复造码
- 如何淘汰失效错误码
- 如何统计哪些错误码是最应该优先治理的

如果没有治理闭环，再好的设计最终也会失控。

## 常见误区

在真正设计 Schema 之前，先说几个很常见的误区。

### 误区一：把 HTTP Status Code 当成错误码

HTTP Status Code 只回答一件事：这次 HTTP 交互在协议层面处于什么结果。它无法完整表达业务语义。

例如两个请求都返回 `400`：

- 一个可能是 token 已过期
- 一个可能是商品 SKU 重复
- 一个可能是参数缺失

这三者的处理策略完全不同，但 HTTP code 是一样的。

所以 HTTP code 可以保留，但它不能替代业务错误码。

### 误区二：把 message 当成协议

很多系统会在上游通过 `contains("token expired")` 之类的逻辑识别错误。这种做法早期很省事，长期一定出问题：

- 文案一改就失效
- 多语言后彻底不可控
- 下游改了大小写、标点、措辞都可能导致判断失败

`message` 应该给人看，`code` 才应该给机器看。

### 误区三：一个系统只保留“最后抛出的错误”

在分布式环境里，最终暴露出来的错误通常不是根因，而是经过多层包装后的结果。

举例来说：

1. 第三方平台返回“token 已失效”
2. 集成服务将其包装为“拉取订单失败”
3. 平台再包装为“请求处理失败”

如果最后只看到 `REQUEST_FAILED`，那对排障几乎没帮助。真正有价值的是：既看到当前层怎么解释，也看到原始错误从哪里开始发生。

### 误区四：每出现一个报错就创建一个新错误码

错误码不是越多越好。过度细分会迅速失控：

- 上下游难以复用
- 文档难维护
- 调用方不知道应该依赖哪个粒度
- 相似问题被拆成几十个码，统计分析反而失去意义

好的实践通常是：先有清晰分类，再在必要时扩展，而不是把每条错误文案都变成独立 code。

## 一套实用的设计原则

在过往的开发中，错误码设计里最重要的是下面五条。

### 1. 机器可判定，人类可理解

错误码必须稳定、短小、语义明确。使用全大写英文下划线（驼峰法也是可以的）命名，例如：

- `AUTH_INVALID_TOKEN`
- `ORDER_NOT_FOUND`
- `UPSTREAM_RATE_LIMITED`
- `INVENTORY_CONFLICT`

它应该满足两个目标：

- 上游系统可以基于它写分支逻辑
- 研发看到它时，不需要翻很多文档就能大致理解问题

### 2. code 稳定，message 可演进

一旦某个错误码对外暴露并被依赖，就不应该轻易变更语义。相反，`message` 可以随着产品、语言、沟通对象不同而调整。

也就是说：

- `code` 是 contract
- `message` 是 presentation，前后端的表示可以有差异

这个边界一定要明确。

### 3. 当前层要有当前层的语义

错误透传不是简单复制。每一层都应该保留“它自己如何理解这个问题”。

例如下游返回 `AUTH_INVALID_TOKEN`，上游不应该生硬复刻一切，而应该根据场景决定：

- 是直接透传给调用方
- 还是包装成更高层的 `ORDER_PULL_DEPENDENCY_FAILED`
- 同时保留原始根因，方便定位

这也是为什么我更倾向于“顶层状态 + 错误传播链”的设计，而不是只保留一个单点 code。

### 4. 根因必须保真

上游可以包装错误，但不能篡改已存在的下游节点信息。否则链路一长，根因就丢了。

对于稳定性建设来说，最有价值的信息通常是：

- 最终对外暴露的错误是什么
- 最初真正失败的那个错误是什么

两者都要保留。

### 5. 局部上下文和全局上下文分离

不是所有信息都适合塞进错误对象里。

- 局部排障信息，例如下游 endpoint、操作对象 ID、限流桶名称，适合放在当前节点 `labels`
- 全链路信息，例如 trace id、tenant id、request id，适合放到日志上下文、trace 系统或请求头里

否则错误对象会越来越重，最终变成一个什么都想装的“垃圾桶”。

## 一个适合分布式系统的错误 Schema

下面这个 Schema 比较适合微服务和集成场景。它的核心思想很简单：

- 顶层字段描述“当前系统最终抛出了什么”
- `error_chain` 描述“这个错误是如何一路传播上来的”

### JSON 示例

```json
{
  "service": "api-platform",
  "http_code": 500,
  "code": "PLATFORM_FAILED",
  "message": "平台处理失败：下游服务异常",
  "error_chain": [
    {
      "service": "auth-service",
      "http_code": 400,
      "code": "AUTH_INVALID_TOKEN",
      "message": "Token 格式错误或已过期",
      "unix_ms": 1714129412000,
      "labels": {
        "token_prefix": "Bearer"
      }
    },
    {
      "service": "user-service",
      "http_code": 502,
      "code": "USER_UPSTREAM_ERROR",
      "message": "调用 Auth 服务获取鉴权信息失败",
      "unix_ms": 1714129412050,
      "labels": {
        "endpoint_called": "/v1/auth/verify"
      }
    },
    {
      "service": "api-platform",
      "http_code": 500,
      "code": "PLATFORM_FAILED",
      "message": "平台处理失败：下游服务异常",
      "unix_ms": 1714129412080,
      "labels": null
    }
  ]
}
```

### 字段说明

顶层字段代表最终出口状态，通常是直接返回给调用方或写入统一日志系统的部分。

| 字段名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `service` | `String` | 是 | 当前最终抛出错误的服务名。 |
| `http_code` | `Integer` \| `Null` | 是 | 当前层映射后的 HTTP 状态码。非 HTTP 场景可为空。 |
| `code` | `String` | 是 | 当前层定义的业务错误码，应在可见范围内稳定唯一。 |
| `message` | `String` | 是 | 当前层给研发或调用方阅读的错误描述。 |
| `error_chain` | `Array<ErrorNode>` | 是 | 从根因到当前层的错误传播链。 |

`error_chain` 中的节点代表错误在各服务中的一个快照：

| 字段名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `service` | `String` | 是 | 该节点对应的服务名。 |
| `http_code` | `Integer` \| `Null` | 是 | 该节点当时抛出的 HTTP 状态码。 |
| `code` | `String` | 是 | 该节点当时抛出的业务错误码。 |
| `message` | `String` | 是 | 该节点当时记录的错误信息。 |
| `unix_ms` | `Integer` | 是 | 节点生成时间，用于还原传播顺序和估算延迟。 |
| `labels` | `Object` \| `Null` | 否 | 当前层独有的排障上下文，建议保持扁平。 |

## 这套 Schema 的几个关键约定

Schema 本身并不复杂，真正重要的是契约。

### 1. `error_chain[0]` 必须是根因

这是最重要的一条约定。

只要这个约定始终成立，那么任何上游系统想快速识别“底层到底出了什么问题”，都可以直接看：

```text
error_chain[0].code
```

这样在做降级、重试、用户提示、指标聚合时都非常直接。

### 2. 传播链只能追加，不能改写

错误一旦从某个服务生成，该节点内容就应该视为只读。上游服务如果需要包装，只能 append 自己的节点，不能改写历史节点。

这样做有两个好处：

- 保证根因保真
- 可以根据各节点时间戳估算错误在链路中的传播和处理耗时

### 3. 顶层字段与链尾节点通常保持一致

实践中，我建议顶层 `service/code/message/http_code` 与 `error_chain` 最后一个节点语义一致。这样阅读和存储都更直观：

- 顶层字段方便快速索引和展示
- `error_chain[-1]` 方便保持完整时序结构

虽然这会有一点信息重复，但换来的是可读性和查询便利，通常值得。

### 4. `labels` 只放局部排障信息

`labels` 的目标不是替代业务对象，也不是复制请求参数，而是给排障提供补充线索。

适合放进去的例子：

- `endpoint_called`
- `shop_id`
- `platform`
- `rate_limit_bucket`
- `retry_count`

不适合放进去的内容：

- 大块响应体,超长 URL
- 敏感 token
- 用户隐私数据
- 会无限膨胀的对象

尤其在稳定性系统里，错误对象会进入日志、DB。字段一旦失控，成本会很快放大。

## 错误码如何分层

真正落地时，我建议至少把错误分成三层，不要把所有问题混在一起。

### 第一层：领域错误

这是最贴近业务语义的一层，例如：

- `ORDER_NOT_FOUND`
- `PRODUCT_STATUS_INVALID`
- `INVENTORY_CONFLICT`
- `SHOP_NOT_AUTHORIZED`

这类错误最适合被产品、客服、运营理解，也最适合被上层业务直接消费。

### 第二层：依赖错误

这是系统与外部依赖交互时产生的抽象，例如：

- `UPSTREAM_TIMEOUT`
- `UPSTREAM_RATE_LIMITED`
- `UPSTREAM_UNAVAILABLE`
- `DEPENDENCY_BAD_RESPONSE`

这类错误的重点是“问题来自依赖”，它们往往驱动重试、熔断、降级和告警策略。

### 第三层：系统错误

这是平台自身的通用故障，例如：

- `INTERNAL_UNEXPECTED_ERROR`
- `DB_TRANSACTION_FAILED`
- `CACHE_UNAVAILABLE`
- `MESSAGE_PUBLISH_FAILED`

这类错误更偏基础设施和工程稳定性。

这样的分层有一个直接好处：调用方可以基于大类先做粗处理，再基于具体 code 做细处理，而不是面对一堆完全扁平的码表。

## HTTP 状态码应该怎么配合

错误码标准化之后，HTTP Status Code 依然重要，但两者分工不同。

我更推荐下面这个原则：

- HTTP code 用来表达协议层结果
- 业务 code 用来表达可执行语义

例如：

| 场景 | HTTP Status | 业务错误码 |
| :--- | :--- | :--- |
| 请求参数不合法 | `400` | `INVALID_ARGUMENT` |
| 未授权或授权失效 | `401` / `403` | `AUTH_INVALID_TOKEN` / `PERMISSION_DENIED` |
| 资源不存在 | `404` | `ORDER_NOT_FOUND` |
| 下游超时 | `504` | `UPSTREAM_TIMEOUT` |
| 下游返回异常 | `502` | `UPSTREAM_BAD_RESPONSE` |
| 系统内部异常 | `500` | `INTERNAL_UNEXPECTED_ERROR` |

### 一个容易争议的问题：应该返回根因 HTTP code，还是最后出口的 HTTP code？

我的建议是：

- 对外接口，优先返回“当前系统视角下最合理的出口状态码”
- 根因 HTTP code 保留在 `error_chain[0].http_code` 里供排障和统计使用

原因很简单。平台或者聚合层在对外提供协议契约时，应该表达“当前请求为什么失败”，而不是机械转发下游的协议结果。

例如下游返回 `401`，但对平台来说这可能本质是“依赖故障”，最终对客户端返回 `502` 反而更合理。否则调用方会误以为是自己的身份失效。

也就是说：

- 对外语义要面向调用方
- 根因语义要保留给内部排障

这两件事不要混为一谈。

## 落地时的几个工程建议

错误码设计成文档很容易，真正难的是在代码里持续执行。

### 1. 统一定义，不要分散手写

错误码最好有统一注册中心，哪怕一开始只是一个代码仓库里的枚举或配置文件，也比各服务自己随手写强。

至少要能支持：

- 查询某个 code 的定义
- 查询它对应的 message 模板
- 查询推荐的 HTTP mapping
- 查询处理建议，例如是否可重试、是否应该告警、是否对用户可见

如果这些信息都散落在各服务代码中，半年后基本没人能说清楚全貌。

### 2. 给错误码附带元属性

很多时候，调用方不只关心 code 本身，还关心策略属性。一个实用的错误码定义，通常可以带上这些元数据：

| 字段 | 作用 |
| :--- | :--- |
| `retryable` | 是否适合自动重试 |
| `alert_level` | 默认告警级别 |
| `user_visible` | 是否适合直接展示给用户 |
| `owner_team` | 首要负责团队 |
| `http_mapping` | 推荐的 HTTP 状态码 |

这样错误码就不只是“分类标签”，而变成可以直接驱动系统行为的规则对象。

### 3. 对未标准化错误做兜底

再完整的码表也无法穷举所有未来错误，所以系统里一定要有兜底码，例如：

- `INTERNAL_UNEXPECTED_ERROR`
- `UPSTREAM_UNKNOWN_ERROR`
- `UNCLASSIFIED_DEPENDENCY_FAILURE`

但要注意，兜底不是终点。所有落到兜底码的错误，都应该进入后续治理清单，否则“兜底”很快就会变成“默认”。

### 4. 让日志、监控、链路追踪都能消费同一套 code

错误码的价值只有在被系统消费时才会体现。至少应该统一到三个地方：

- 日志检索：按 code 聚合问题
- 监控告警：按 code 统计错误率和趋势
- 链路追踪：在 trace/span 上标注 code 和根因 code

如果码表只存在于接口返回里，而日志和监控还在依赖 message 搜索，那标准化的收益会被大幅削弱。

## 如何持续运营这套错误码

我更关心的其实不是“第一次如何设计”，而是“半年后它还能不能继续可用”。

### 指标一：错误标准化覆盖率

最值得长期追的一个指标是：

```text
标准化错误数 / 全部错误数
```

或者更精确一点：

```text
已映射到稳定 code 的错误请求数 / 全部错误请求数
```

这个比例越高，说明你的错误体系越成熟；比例越低，说明线上仍有大量问题停留在“只有异常，没有标准语义”的阶段。

### 指标二：未标准化错误 Top N

除了覆盖率，还要持续看未标准化错误的 Top N，例如：

- 最近 7 天最常见的未标准化的 error messages 是什么
- 哪些 message 频繁出现但还没有标准 code
- 哪些系统是未标准化错误的主要来源

这张表通常比单纯开会讨论更有效，因为它能直接告诉团队“下一批最值得补的错误码在哪里”。

### 指标三：错误码复用率

如果一个团队每次新增逻辑都倾向于申请新 code，而不是复用已有分类，那么码表会迅速膨胀。

因此需要明确一个原则：

新增错误码之前，先判断是否可以复用已有 code。

只有在以下情况才值得新增：

- 现有 code 无法表达该语义
- 它需要不同的处理策略
- 它需要独立统计和运营

否则优先复用。

### 指标四：高频错误码治理优先级

不是所有错误码都值得同等投入。运营上更有效的做法是把错误码按影响排序：

- 高频但可自动恢复的，优先做自动化
- 高频且影响用户的，优先做产品和工程修复
- 低频但影响巨大的，优先做预案和告警升级

这样错误码体系就和稳定性治理真正连起来了，而不是停留在文档层。

## 我会避免的几个反模式

最后说几个我在实践里会刻意避免的反模式。

### 1. 用数字码但没有语义

像 `10023`、`20451` 这种纯数字码，除非团队有很成熟的配套平台，否则维护成本会很高。研发离开查询平台就无法直观理解含义，排障效率偏低。

对大多数中小团队而言，可读字符串通常更实用。

### 2. 一个错误码覆盖多个完全不同的原因

如果 `SYNC_FAILED` 同时可能表示：

- token 失效
- 参数错误
- 限流
- 数据格式错误

那它对自动化处理的帮助很弱。抽象可以有，但不能抽象到失去行动意义。

### 3. 把下游原始错误直接暴露给外部用户

下游错误往往技术味很重，甚至包含不稳定字段。直接原样透出会带来三个问题：

- 用户看不懂
- 契约不稳定
- 容易泄露内部实现细节

更好的做法是对外输出当前层可理解的 code/message，尤其是在前端，对内保留完整链路。

### 4. 没有 owner

错误码不是“定义完就结束”的资产。每一类高频错误最终都应该能找到负责人，否则统计做得再漂亮，也没人持续投入治理。

## 总结

错误码标准化的核心，不是把异常换一个名字，而是把“失败”从一段临时的技术文本，变成一套可识别、可传播、可运营、可治理的系统语言。

如果只追求“有一份错误码表”，最后大概率会流于形式；真正有用的是让它同时服务于：

- 调用方自动化处理
- 研发排障定位
- 运营和客服沟通
- 监控告警和稳定性治理

在分布式系统里，我比较推荐的落地方向是：

- 用稳定的业务 code 表达语义
- 用 HTTP code 表达协议层结果
- 用 append-only 的 `error_chain` 保留根因传播过程
- 用统一治理机制持续补齐、复用和收敛错误码

做到这一步，错误码才不只是“接口字段”，而会真正成为稳定性体系的一部分。
