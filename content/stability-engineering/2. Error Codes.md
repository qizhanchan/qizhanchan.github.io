
# 错误码标准化的由来
错误码不等同于 HTTP Status Code，长期来看都是业界难题，并没有银弹来解决这个问题
1. 不同系统之间，通常要识别这个错误，才能进行下一步处理，重试，抛出错误等
2. 单纯通过错误信息抛出，可能会太技术化，对于商家来说并不友好，所以在此基础上可以给出更多的抽象
所以需要标准化，最好有一个地方来管理生成，查询


# 错误码设计
此 Schema 专为分布式/微服务架构设计，采用**时序追加**的链式结构，精简去除了外部依赖字段，旨在提供纯粹的错误溯源能力。

#### 1. JSON 数据示例

```json
{
  "service": "api-gateway",
  "http_code": 500,
  "code": "GATEWAY_DEPENDENCY_FAILED",
  "message": "网关处理失败：下游服务异常",
  "error_chain": [
    {
      "service": "auth-service",
      "http_code": 400,
      "code": "AUTH_INVALID_TOKEN",
      "message": "Token 格式错误或已过期",
      "unix_ms": 1714129412000,
      "labels": {
        "token_prefix": "Bearer"
      }
    },
    {
      "service": "user-service",
      "http_code": 502,
      "code": "USER_UPSTREAM_ERROR",
      "message": "调用 Auth 服务获取鉴权信息失败",
      "unix_ms": 1714129412050,
      "labels": {
        "endpoint_called": "/v1/auth/verify"
      }
    },
    {
      "service": "api-gateway",
      "http_code": 500,
      "code": "GATEWAY_DEPENDENCY_FAILED",
      "message": "网关处理失败：下游服务异常",
      "unix_ms": 1714129412080,
      "labels": null
    }
  ]
}
```

---

#### 2. 字段详细说明

**顶层结构 (Top-Level Object)**
顶层字段描述的是**当前最终抛出错误的服务**的状态，通常用于被直接调用方读取。

| 字段名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| **`service`** | `String` | 是 | 当前抛出该错误的微服务名称（如 `api-gateway`）。 |
| **`http_code`** | `Integer` \| `Null` | 是 | 当前层转换后的 HTTP 状态码。若当前服务非 HTTP 协议或底层纯业务异常，可传 `null`。 |
| **`code`** | `String` | 是 | 当前层定义的**业务错误码**（如 `GATEWAY_DEPENDENCY_FAILED`），必须具备全局唯一性。 |
| **`message`** | `String` | 是 | 当前层给出的开发者可读的错误描述信息。 |
| **`error_chain`** | `Array<ErrorNode>`| 是 | 错误传播链路的核心数组，记录从源头到当前的完整异常快照。 |

**链节点结构 (ErrorNode Object)**
`error_chain` 数组中的每一个元素代表错误流转经历的一个服务节点。

| 字段名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| **`service`** | `String` | 是 | 发生或中转该错误的服务名称。 |
| **`http_code`** | `Integer` \| `Null` | 是 | 该服务在抛出错误时对应的 HTTP 状态码。 |
| **`code`** | `String` | 是 | 该服务在当时抛出时的原始业务错误码。 |
| **`message`** | `String` | 是 | 该服务在当时抛出时的原始错误描述信息。 |
| **`unix_ms`** | `Integer` | 是 | **核心字段**：该节点生成错误时的 **Unix 毫秒级时间戳**，用于表征错误发生的精确时间。 |
| **`labels`** | `Object` \| `Null` | 否 | **核心字段**：扁平化的键值对（Key-Value），用于记录当前服务层特有的报错上下文（如调用的下游 URL、特定参数等），契合监控系统的时序标签体系。 |

---

#### 3. 核心设计契约与约定

1. **Root Cause（根本原因）约定**
    * **强制规则**：`error_chain` 数组的**索引 0 (`error_chain[0]`) 必须是 Root Cause（底层根因）**。
    * **执行逻辑**：当网关或顶层业务需要识别底层错误并做出兜底动作时，直接读取 `error_chain[0].code` 进行判定即可。
2. **时序与追加写入 (Append-Only)**
    * 底层服务在最初生成错误时，创建 `error_chain` 并压入第一个节点（同时也是 `unix_ms` 最小的节点）。
    * 上游服务在捕获该错误并向更上层抛出时，**不得修改** `error_chain` 中已有的节点数据，只能将自己的状态作为一个新节点 **Append（追加）** 到数组末尾。
    * 通过对比不同节点的 `unix_ms`，可以直接计算出错误在各服务间传递的网络与处理延迟。
3. **元数据分离**
    * `labels` 仅用于存放**局部、特定于该层的**排错线索（如发生错误时的特定条件）。
    * 跨越整个生命周期的全局信息（如 Trace ID、User ID 等）不包含在此 Schema 内，应统一交由日志系统（如 MDC context）或请求头（Headers）进行维护。


# 如何持续运营
错误被标准化成错误码的比例报表，以及未标准化的错误
- 因为错误都是无法穷举的，会随着版本迭代，功能叠加而增加。而且实际生产环境并非单一系统单一服务，我们对接的系统越来越多，则错误会越积越多
- 对于未标准化的错误，需要定期安排人力来识别，并标准化

错误码要优先复用，而不是每次都申请一个，否则会冗余，上下游在使用的时候会特别痛苦
